A working prototype of the MIP*=RE compression step

Compress, Explained

Ji, Natarajan, Vidick, Wright and Yuen prove MIP* = RE by building a machine that eats a verifier's source code and returns a verifier that does the same job exponentially faster. This page is a tour of that machine as we have actually built it in Julia — every instrument below runs on objects the test suite printed, and every number is stamped with what it is allowed to claim.

The one law of this page: nothing is stated more strongly than claims/CLAIMS.md allows. Four chapters describe machinery that is designed but has never run; they say so in the margin, in the figure, and in the text. Sixteen instruments, six clips, one machine room.

§1

Turing machinesdocs/analytic part1a §1.2

A verifier is a finite transition table. Everything the paper says about its code, time and simulation refers to this object.

The analytic document opens with a machine so small it fits in five rows: M₌, which reads one bit off each of two input tapes and writes their equality bit to an output tape. It has two non-halting states and one halting state, four tapes, and a catch-all row that makes the table total. On legal one-bit inputs it halts after exactly three transitions.

What the paper needs from this

A verifier's description ⟨V⟩ is a finite string spelling out such a table, and Time counts transitions. Compression is a statement about that string and that count — not about the function the machine computes. A universal machine U reading ⟨M⟩ and x simulates M on x; the whole construction is bookkeeping about how long that takes and how long the strings are.

Lambda terms and quotationpart1b §3–§4C18 SKETCH

Recursion is not a name pointing at itself. It is a finite term that grows only when you run it.

The self-referential verifier at the heart of the Halting reduction is a fixed point. In the lambda calculus that is Y = λF.(λx.F(xx))(λx.F(xx)): no recursive name appears anywhere in the syntax, and recursion is produced when two copies meet. The project's evaluator is deterministic call-by-value, so its constructor must behave like the eta-delayed Z, and the implementation closes a single self_code hole rather than materialising the unfolding.

Instrument · β-reduction with de Bruijn indicespart1b §4.3 · λx.λy.x y ≡ λ.λ.(1 0)

A bound occurrence is replaced by the number of binders between it and its binder, counting the nearest as zero. Both λa.λb.a b and λx.λy.x y serialise to the same tree — which is why canonical bytes exist at all, and why inserting a closed term can never capture a name.

What is claimed, and what is not

C18 (SKETCH) records the s-m-n transformer, Kleene's e_Q = s(p,p), and the statement that the paper's explicit F(F,M,λ,…), the Kleene fixed point and DM,λ = YCode(ΨM,λ) are three descriptions of the same partial function, all of size O(|M| + log λ + 1). That is a written derivation, not a verified one. The extensional fixed-point value argument stays CITED. Note also that §8's constant is c_Y = 3 while the TB3 implementation charges c_Y = 1 — TB3 is evidence for that instantiation, not for §8's constants.

Fuel and the CEK machinepart2a §8.5C16 SKETCH

Every reduction costs one unit. That is what turns "number of steps" into a resource the compression theorem can budget.

Evaluation is a deterministic call-by-value CEK machine with a fuel counter. One charged transition is one fuel unit, so a bounded trace has exactly one row per unit spent. Running out is not an error — it is the outcome OutOfFuel, alongside Value and SortError. The evaluator never throws.

What is claimed, and what is not

C16 (SKETCH): the CEK relation is a function, so evaluation is single-valued; fuel is monotone; and Eval_L(Quote(t), u; f + h(d,u)) = eval_L(t, u; f). TB3's tests (a) and (b) are the first machine evidence for it — on fixtures, with a coarser charge than §8's, byte units rather than the ν-encoding's bits, and c_Y = 1. There is no verdict promoting C16, so it stays SKETCH.
